# FastAPI-бэкенд без базы данных

Бэкенд принимает DOCX, вызывает `formal_check` и `formal_fix`, сохраняет
исходники, исправленные копии и отчёты на локальном диске без ограничения срока
для последующей аналитики и возвращает JSON или исправленный файл.
Веб-интерфейс NormaCheck доступен на `/`; конфигурации публикации нет.

Для разработки фронтенда см. [контракт интеграции](docs/FRONTEND.md),
для архитектуры и принятых решений — [обзор проекта](docs/PROJECT.md).
ИИ-разработчику также следует прочитать [AGENTS.md](AGENTS.md).

## Запуск

Нужен Python 3.12. Команды выполнять из корня проекта:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock
uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Сайт доступен по адресу `http://127.0.0.1:8000/`, API — на том же origin,
проверка доступности — `GET /health`, OpenAPI-схема — `GET /openapi.json`.
HTML находится в `frontend/index.html`, статика — в `frontend/assets/` и
доступна по `/assets/`. Node, установка npm-пакетов и сборка не нужны.
`storage/` не публикуется. Сохраняются CSP, подписанная HttpOnly-cookie и CSRF.
Старое указание Python 3.9 в README относится только к модулям обработки.

`--workers 1` означает один процесс HTTP-приложения, **а не один документ**:
разные документы обрабатываются параллельно в отдельных дочерних процессах.
По умолчанию доступны два обработчика. Например, для четырёх:

```bash
MAX_CONCURRENT_JOBS=4 uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Выбирайте параллельность по доступным CPU и RAM. В Linux каждый обработчик
ограничен настройкой `WORKER_MEMORY_MB`; API и загрузкам тоже нужна память.
При занятых обработчиках новая операция получает 503 с `Retry-After: 5`.
Очереди нет. Просмотр готовых отчётов не занимает слоты обработки.
Один и тот же документ нельзя одновременно исправлять несколькими запросами.

## API

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/session` | Получить cookie анонимной сессии и CSRF-токен |
| `POST /api/documents` | Загрузить один DOCX, дождаться проверки, получить JSON; 201 |
| `GET /api/documents/{id}` | Получить состояние и актуальный отчёт |
| `POST /api/documents/{id}/fix` | Исправить исходник и полностью проверить копию |
| `GET /api/documents/{id}/download` | Скачать успешно проверенную исправленную копию |

Изменяющие запросы требуют cookie и заголовок `X-CSRF-Token`. Документы доступны
только загрузившей сессии, без регистрации и серверного реестра пользователей.
Cookie подписана; владелец документа записан в его метаданных. Смена браузера
или удаление cookie лишает доступа; восстановления доступа в MVP нет.
Срок cookie — 7 суток, обновляется при вызове `/api/session` с действующей
сессией. Истечение cookie не удаляет документы, но без прежней сессии доступ
к ним через пользовательский API восстановить нельзя.

Пример последовательности запросов:

```bash
# 1. Получить cookie и CSRF-токен.
curl -sS -c /tmp/docx-cookies.txt http://127.0.0.1:8000/api/session

# 2. Подставить csrf_token из ответа и путь к своему документу.
curl -sS -b /tmp/docx-cookies.txt \
  -H 'X-CSRF-Token: ВАШ_CSRF_TOKEN' \
  -F 'file=@/полный/путь/document.docx' \
  http://127.0.0.1:8000/api/documents

# 3. Подставить document_id из ответа.
curl -sS -b /tmp/docx-cookies.txt \
  http://127.0.0.1:8000/api/documents/ВАШ_DOCUMENT_ID

# 4. Выполнить автоисправление и повторную проверку.
curl -sS -X POST -b /tmp/docx-cookies.txt \
  -H 'X-CSRF-Token: ВАШ_CSRF_TOKEN' \
  http://127.0.0.1:8000/api/documents/ВАШ_DOCUMENT_ID/fix

# 5. Скачать исправленный DOCX.
curl -f -b /tmp/docx-cookies.txt \
  -o /tmp/corrected.docx \
  http://127.0.0.1:8000/api/documents/ВАШ_DOCUMENT_ID/download
```

Ответ проверки содержит `document_id`, `filename`, `state`, `current_version`,
`report`, `warnings`, `limitations`, `last_error`, даты, версии проверяющего
модуля и набора требований, а также `download_url` после успешного исправления.
`report` сохраняет исходный контракт `formal_check`: `standard` и `findings`.
Внутренние пути, секреты и `owner_id` в API не возвращаются.
Всегда возвращается `expires_at: null`; в `/api/session` значение
`retention_hours: null` означает постоянное хранение.

Состояния: `checking`, `checked`, `fixing`, `fixed`, `failed`.
`current_version`: `null`, `original` или `corrected` — последняя успешно
проверенная версия. Если исправление или повторная проверка упали, исходный
отчёт остаётся доступным, скачивание непроверенной копии запрещено.
Повторный вызов `/fix` после успеха возвращает готовый результат.

Ошибки: `{"error":{"code":"...","message":"..."}}`.
Основные HTTP-коды: 401 — нет сессии; 403 — неверный CSRF; 404 — нет документа
или доступа; 405 — метод не поддерживается (в том числе `DELETE`);
409 — операция конфликтует или копия не готова;
413 — размер превышен; 415 — другой формат; 422 — некорректный DOCX;
500 — ошибка обработки; 503 — все обработчики заняты; 504 — тайм-аут;
507 — хранилище заполнено.

## Файловое хранение

```text
storage/
  .session-secret
  .server.lock
  documents/
    <uuid>/
      metadata.json
      original.docx
      original-report.json
      original-warnings.json
      corrected.docx
      corrected-report.json
      corrected-warnings.json
```

Исходный DOCX не меняется. Исправитель самостоятельно получает точные объекты
через `inspect_document`; JSON и фрагменты из запроса не используются как
инструкции изменения. После `fix_document` выполняется полный `check_document`.

Обработчик пишет в отдельную временную папку. API валидирует результат,
публикует файлы и последним обновляет метаданные. JSON записывается атомарно.
Временные результаты при сбое не становятся доступными для скачивания.

Все принятые документы хранятся постоянно в одном основном каталоге.
В приложении нет эндпоинта удаления, команды очистки и настроек, которые
включают удаление по времени. `DELETE /api/documents/{id}` возвращает 405.
Старые переменные окружения `RETENTION_HOURS` и `CLEANUP_INTERVAL_SECONDS`
больше не используются и не могут включить удаление.
Исходники, исправленные копии и отчёты можно читать из этих же папок для
аналитики; отдельного архива нет. При запуске прежние сроки `expires_at`
заменяются на `null`, включая уже просроченные, но ещё не удалённые загрузки.
Содержимое DOCX и отчётов при этом не меняется. Уже удалённые файлы не восстанавливаются.

Ошибка проверки или исправления не удаляет загруженный исходник. Повторная
загрузка того же файла создаёт отдельную запись и сохраняет оба исходника.
Если перенос принятой загрузки в основное хранилище прервался, полученные
байты остаются в `.upload`, а метаданные помечаются `failed`.
Файлы, отклонённые до приёма из-за формата, размера, занятых обработчиков
или недостатка места, не считаются сохранёнными загрузками.
Служебные временные результаты обработки и временные JSON очищаются;
это не затрагивает исходники и опубликованные DOCX и отчёты.
При перезапуске незаконченные операции получают `failed`; готовые отчёты
сохраняются. Автоматического продолжения прерванных операций нет.

Одновременно запустить два API с одним хранилищем нельзя: блокировка защищает
выполняющиеся операции от восстановления вторым процессом.

## Переменные окружения

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `STORAGE_DIR` | `storage` в корне | Папка данных |
| `MAX_CONCURRENT_JOBS` | `2` | Параллельные DOCX-операции |
| `PROCESSING_TIMEOUT_SECONDS` | `60` | Время проверки либо исправления вместе с повторной проверкой |
| `WORKER_MEMORY_MB` | `768` | Лимит адресного пространства обработчика в Linux |
| `MAX_UPLOAD_MB` | `20` | Максимальный размер DOCX, МиБ |
| `MAX_STORAGE_MB` | `2048` | Бюджет хранения документов, МиБ |
| `APP_SECRET` | Локальный файл | Секрет подписи сессий, от 32 символов |
| `COOKIE_SECURE` | `false` | Передавать cookie только по HTTPS |
| `ALLOWED_HOSTS` | `localhost,127.0.0.1` | Разрешённые имена Host через запятую |

Локально секрет автоматически создаётся в `storage/.session-secret`.
Не публикуйте его. Смена секрета прекращает доступ ранее выданных сессий.
Для `COOKIE_SECURE=true` требуется явно задать `APP_SECRET`.
Переменные читаются из окружения, `.env` автоматически не загружается.

DOCX дополнительно ограничен 2048 частями, распакованным размером 256 МиБ,
размером части 64 МиБ и XML-части 32 МиБ. Макросы, зашифрованные ZIP,
повторяющиеся части и чрезмерное сжатие отклоняются. Linux ограничивает память
и CPU дочерних процессов; на macOS действуют лимиты файлов и тайм-аут родителя.
Бюджет хранилища учитывает резерв для параллельных загрузок, но не является
жёсткой квотой файловой системы: временные файлы могут кратковременно превышать
бюджет. Следите за свободным местом.
При заполнении бюджета хранилища новые загрузки отклоняются с HTTP 507;
старые документы для освобождения места автоматически не удаляются.
Для накопления курсовых увеличивайте `MAX_STORAGE_MB` по доступному диску.

## Тесты

```bash
python -m pip install -r requirements-dev.txt
python -m pytest tests -q
```

Интеграционные тесты генерируют DOCX и вызывают настоящие модули. Проверяются
полный цикл, неизменность исходника, скачивание, доступ разных сессий, CSRF,
ошибки входа, лимиты, тайм-аут, восстановление, отсутствие удаления из API,
постоянное хранение, игнорирование старых настроек очистки, сохранение файлов
при ошибке проверки и полученных байтов при сбое переноса загрузки,
одновременная обработка двух и четырёх документов, блокировка изменения одного
документа и отказ от публикации некорректного повторного отчёта.
Старый набор тестов модулей, упомянутый в README, в этой копии отсутствует.

Проверки фронтенда без дополнительных зависимостей (Node 22+):

```bash
node --test tests/frontend.test.mjs
```

Они проверяют поиск и сочетание фильтров, изоляцию ручных отметок между
версиями отчётов и обработку ошибок HTTP. Python-тесты также проверяют
раздачу интерфейса с CSP, доступность API и закрытость приватных файлов.

`requirements.lock` фиксирует проверенные runtime-зависимости для Python 3.12.
`requirements.txt` содержит прямые зависимости с диапазонами для намеренного
обновления; после обновления нужно пересоздать lock и повторить тесты.

Ограничения проверки возвращаются отдельно от замечаний. Пустой отчёт не
доказывает полного соответствия СТП. Смысловой анализ, OCR, рендеринг страниц
и пересчёт содержания не выполняются. Передача документов внешним сервисам
не производится. Распределённая обработка на нескольких серверах не поддержана.
