# Формальная проверка DOCX — MVP

В проект добавлен **бэкенд на FastAPI**: API загрузки DOCX, формальной проверки,
автоисправления, повторной проверки и скачивания. **Без базы данных**, с
параллельной обработкой разных документов в отдельных процессах.
Принятые исходники, исправленные копии и отчёты хранятся постоянно
в основном файловом каталоге для последующей аналитики. Возможности удалить
загрузки через API, по сроку хранения или командой очистки нет.
Веб-страницы и публикация не добавлены. Установка, запуск и примеры запросов
описаны в [BACKEND.md](BACKEND.md).
Для продолжения разработки в новом чате начните с [AGENTS.md](AGENTS.md),
[обзора проекта](docs/PROJECT.md) и [контракта для фронтенда](docs/FRONTEND.md).
Ниже сохранено описание исходных модулей; старые ссылки на `docs/tz_my/`,
`docs/1.docx`, `docs/2.docx`, `reports/` и HTML-шаблон относятся к полной
исходной поставке. Эти материалы в текущей копии отсутствуют.

Модуль проверяет доступные по DOCX требования СТП 01–2017 и возвращает замечания
по 31 правилу с исходными ID F01–F36, кроме исключённых F11, F13, F14, F17 и F21.
Telegram, LLM, OCR и рендеринг не используются. Исходный файл не изменяется.
Сеть во время проверки не нужна.

Модуль `formal_fix` сохраняет исправленную копию DOCX без возвращаемого объекта.
Поддержаны F01, F03, однозначные случаи F04, отступы F05, выравнивание F06
и промежуток с одним существующим пустым абзацем после заголовка F07. Итоговый отчёт
получают отдельным вызовом `formal_check`. Подробности — в
[плане и контракте автоисправления](docs/tz_my/plan-formal-fix-mvp.md).

**Изменение требований от 22.10.2026:** из F07 удалена рекомендация начинать
раздел с новой страницы; проверка пробельной строки после заголовка сохранена.
Проверки F11 (оформление перечислений), F13 (математические знаки в тексте),
F14 (запись чисел), F17 (расположение и промежутки формул) и F21 (оформление
расшифровок «где») исключены целиком.
Остальные ID не перенумеровываются: в реестре остаётся 31 правило.
Сохранённые ранее отчёты автоматически не пересчитываются. После обновления
нужно заново проверить DOCX; JSON с любым из исключённых правил
не соответствует текущему списку допустимых правил. В прототипе перезапустите сервер и загрузите файл заново.

**Исключение заказчика, согласованное 21.10.2026:** F03 требует одинарный
межстрочный интервал **1.0** для обычного текста. Проверяются итоговые свойства
абзаца с учётом стилей: `lineRule=auto`, `line=240`. Отсутствующие свойства
разрешаются через наследование и стандартные значения OOXML. Интервалы «точно»
и «минимум» в пунктах не считаются одинарными. Это локальное требование заказчика,
а не утверждение о фиксированном интервале в СТП. Исходная норма о вместимости
40 ± 3 строки на странице без рендеринга не проверяется.

**Уточнение заказчика от 21.10.2026 для F05:** у нумерованных заголовков
разделов первого уровня проверяются настройки Word «Абзац» → «Отступ»:
слева **1,25 см**, справа **0 см**, особый — **«Выступ» на 0,5 см**.
Учитываются прямые настройки, стили и автоматическая нумерация. Это отдельная
проверка, а не требование обычного отступа первой строки. Значение 1,27 см
слева для этих заголовков не принимается. Проверка не распространяется на
подразделы, ненумерованные «Введение» / «Заключение», содержание и обозначения
приложений. Отступы в знаках дают замечание для ручной проверки. Фактическое
выравнивание продолжения многострочного заголовка по схеме приложения Л
без рендеринга не подтверждается. Числа 1,25/0/0,5 см зафиксированы по
настройкам заказчика, а не как дословная цитата СТП. Источник уточнения —
визуальное изучение приложения Л заказчиком.

В F05 проверяются только согласованные настройки окна Word: слева 1,25 см,
справа 0 см, выступ 0,5 см. Дополнительное требование к отступу продолжения
заголовка не вводится. Технические координаты OOXML приводятся к представлению
Word для Mac: `left/start − hanging` при выступе. Пересчёт одинаков для
автоматических номеров и номеров, набранных в тексте заголовка вручную.
В замечаниях используются привычные поля «Слева», «Справа», «Особый».

Для связанной со стилем нумерации учитывается особенность Word для Mac,
проверенная в окне «Абзац» на разделе 4 документа заказчика: если уровень
нумерации ссылается на стиль через `w:pStyle`, а в самом абзаце нет `w:numPr`,
левый и особый отступы берутся из стиля, даже при наличии других значений
`w:ind` в абзаце. Явная нумерация в самом абзаце и отмена `numId=0` сохраняют
свои правила; правый отступ продолжает учитывать прямую настройку.
Это совместимость разбора для F05, а не новая норма СТП и не изменение
общего наследования форматирования для других проверок. Без рендеринга
совмещение начала строк многострочного заголовка не подтверждается.

**Пояснение ректората, переданное заказчиком 21.10.2026:** обычный текст
пояснительной записки выравнивается **по ширине**, названия нумерованных разделов
и подразделов — **по левому краю**. Ненумерованные названия («Содержание»,
«Реферат», «Введение», «Заключение», «Список использованных источников»,
«Приложения», обозначения и названия отдельных приложений) — **по центру с отступами слева и справа 0 см
и без особого отступа** («Нет» / «отсутствует»). Полужирное начертание названий обязательно; размеры
шрифта заголовков разделов и подразделов остаются рекомендацией. После названия
до текста нужна одна пробельная строка: один пустой абзац либо эквивалентный
интервал. Отсутствие промежутка — ошибка; сомнительный размер интервала — review.
Выравнивание продолжения многострочного названия по началу текста первой строки
без рендеринга не подтверждается; явный перенос названия направляется на review.
Левый и правый отступы проверяются независимо от особого отступа первой строки,
с учётом наследования из стилей. Поэтому «Слева: 1,25 см» при «Особый: Нет»
у ненумерованного заголовка тоже является ошибкой. В JSON для боковых отступов
используются свойства `heading_left_indent` и `heading_right_indent`, для особого —
`heading_first_line_indent`. Отступы в знаках направляются на ручную проверку.
При действующей отмене автоматической нумерации (`w:numId="0"`) отступы
из родительских стилей не наследуются. Явные отступы в самом отменяющем
источнике и последующих настройках сохраняются; шрифт, выравнивание и
межстрочный интервал продолжают наследоваться. Поэтому выступ из стиля
«Заголовок 1» не создаёт ложную ошибку у ненумерованного «Введения».
Это пояснение заменяет прежнюю интерпретацию F06 о выравнивании текста подразделов
слева. F03 по-прежнему требует интервал 1.0; настройки F05 и исключение F04 для
продолжений после формул сохранены. Формулы, подписи, таблицы, списки, примечания,
библиографические записи и код сохраняют применимые правила. Расшифровки «где»
по-прежнему распознаются как специальная область, но их оформление не проверяется;
реферат распознаётся как необязательная область обычного текста.

**Продолжение предложения после формулы (F04):** нулевой отступ не считается
ошибкой, если обычный текст со строчной буквы продолжает незавершённое
предложение через распознанную редактируемую формулу. Учитывается пунктуация
внутри формулы и рядом с её номером; пустые абзацы между фрагментами пропускаются.
Перед формулой должно быть обычное незавершённое предложение в том же разделе.
Заголовки, таблицы и другие содержательные блоки прерывают связь. Если признаки
неоднозначны, вместо требования добавить отступ выдаётся `review` с условной
инструкцией. Новый абзац с прописной буквы после формулы, завершающей предложение,
по-прежнему требует обычного абзацного отступа. Ненулевые неверные отступы
проверяются как прежде. Это локальная эвристика для F04: текст остаётся обычным
для проверок шрифта, межстрочного интервала и выравнивания. Строки «где» распознаются отдельно и не проверяются
как обычные текстовые абзацы; проверка их оформления F21 удалена.
Изображения формул не распознаются; смысловая связь не доказана одной лишь
близостью фрагментов.

**Уточнение заказчика от 21.10.2026 для F22:** между рисунком и подписью
«Рисунок N – Наименование» нужна одна пробельная строка. Для встроенных
рисунков («В тексте») проверяется один пустой абзац либо интервал в одну
строку после рисунка / перед подписью. Пустая строка перед рисунком,
интервал перед рисунком и интервал после подписи не засчитываются.
В общем абзаце рисунка и подписи учитываются явные переносы: два переноса
оставляют одну пустую строку. Проверка действует также для продолжений
«лист N» и рисунков в приложениях. Отдельная норма межстрочного интервала
пустого абзаца не вводится; точная высота промежутка без рендеринга не измеряется.

Подтверждённое отсутствие промежутка — `error`; несколько пустых строк,
интервал в пунктах, автоматические интервалы, разрывы, плавающие или старые
рисунки и смешение рисунка с другим текстом — `review`. Привязка рисунка к
подписи не проходит через текст, заголовки, таблицы и границы секций.
Если рисунок перед подписью не удалось связать с ней, это отмечается в логе,
а отсутствие пробельной строки не утверждается. Рисунки и подписи внутри
таблиц остаются вне этой проверки MVP. Замечание привязано к тексту подписи
со свойством `figure_caption_gap`; HTML показывает его по-русски.
Уточнение о пробельной строке указывается в основании F22 отдельно от пунктов СТП.

Разрывы страниц, колонок и сохранённые Word метки переноса учитываются только
между последним рисунком и началом подписи. Метка `lastRenderedPageBreak`
перед рисунком описывает предшествующий перенос страницы и не делает
корректную пробельную строку после рисунка неоднозначной. Разрыв после начала
подписи также не относится к её ведущему промежутку.

## Быстрый запуск

Python 3.9 или новее. Выполнять из корня проекта:

```bash
cd /Users/andrej/dev/nk1
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt

.venv/bin/python -m formal_check docs/1.docx \
  --output reports/1.json --log reports/1.log

.venv/bin/python -m formal_check docs/2.docx \
  --output reports/2.json --log reports/2.log
```

`--output` обязателен. Каталоги результатов создаются автоматически. Без `--log`
диагностика идёт в stderr. В stdout служебный текст не выводится.

- Код завершения **0**: проверка закончилась, в том числе если найдены нарушения.
- Код завершения **2**: неверный вход, ошибка чтения, проверки или записи.
- JSON записывается атомарно после завершения всех правил и валидации результата.
  При сбое новый частичный отчёт не публикуется; ранее существовавший JSON сохраняется.
- DOCX, JSON и журнал должны иметь разные пути. Проверяются также совпадения через
  символические и жёсткие ссылки.

## Автоматическое исправление оформления

Запуск из корня проекта:

```bash
.venv/bin/python -m formal_fix docs/2.docx --output reports/2-corrected.docx

.venv/bin/python -m formal_check reports/2-corrected.docx \
  --output reports/2-after.json --log reports/2-after.log

.venv/bin/python -m formal_check.viewer reports/2-after.json \
  --output reports/2-after.html
```

`--output` (или `-o`) обязателен и должен указывать на другой DOCX. Каталог
создаётся автоматически. Код завершения `formal_fix`: **0** — копия сохранена,
**2** — ошибка; диагностика идёт в stderr, stdout остаётся пустым. Сам модуль
исправления не создаёт JSON или HTML. Для обновления списка замечаний используйте
результат отдельного вызова `formal_check`, а не число выполненных операций.

Пример вызова из Python, в том числе из серверного слоя FastAPI:

```python
from formal_check import check_document, CheckError, DocumentReadError
from formal_fix import fix_document, FixError

fix_document(original_path, corrected_path)  # возвращает None
after_report = check_document(corrected_path)
# Сервер сохраняет after_report в after.json и возвращает его интерфейсу.
# corrected_path сервер использует для скачивания исправленного документа.
```

Исключения `DocumentReadError`, `CheckError`, `FixError` нужно обработать в
вызывающем коде. Ошибка повторной проверки не является пустым списком замечаний:
при сбое сервер не должен выдавать файл как успешно проверенный. HTTP-сервер
и серверный API реализованы в пакете `app`;
см. [инструкцию бэкенда](BACKEND.md). Веб-интерфейса нет.

| Правило | Что исправляется |
|---|---|
| F01 | Размер страницы А4 и неверные поля конкретной секции; допустимые увеличенные левое/правое поля сохраняются |
| F03 | Одинарный межстрочный интервал обычного текста с учётом наследования |
| F04 | Неверный отступ первой строки обычного текста → 12,5 мм; допустимые 12,7 мм и исключения после формул сохраняются |
| F05, часть | У подразделов — выступ и табуляция, чтобы продолжение начиналось под текстом; у пунктов третьего и четвёртого уровней — отступ первой строки 12,5 мм; у разделов — прежние настройки 1,25/0/0,5 см |
| F06, часть | Выравнивание обычного текста и распознанных заголовков; нулевые боковые и особый отступы ненумерованных названий в области F06 |
| F07, часть | У единственного обычного пустого абзаца после заголовка — одинарный интервал, «До»/«После» 0 пт; после заголовка и перед следующим блоком — 0 пт; дополнительные интервалы в строках и автоматические интервалы выключаются |

Операции применяются только к поддерживаемым замечаниям `error`. Не исправляются
`review`, `recommendation`, последовательность и значения номеров F05, шрифты,
содержательный текст,
формулы, таблицы и специальные названия по F09/F30/F31. Пропускаются неоднозначные
объекты, заблокированные элементы управления содержимым, области с исправлениями
Word или неподдерживаемыми вложенными объектами. Причины пропуска записываются
в журнал. При исправлении размера страницы задаётся книжная ориентация.

Отступы нумерованных заголовков F05 исправляются локально, без изменения общего
стиля и определения списка. Если Word берёт отступы из связанного с нумерацией
стиля и игнорирует прямую настройку, существующие `numId` и уровень закрепляются
в самом абзаце. Номера сохраняются. Для нумерованного заголовка технический
левый отступ OOXML равен сумме 1,25 см и выступа 0,5 см; в проверке он приводится
к настройке Word «Слева: 1,25 см», включая номер, набранный вручную.
Отступы в знаках остаются для ручной проверки.

**Дополнение заказчика от 22.10.2026:** у подразделов второй и последующие
строки начинаются под текстом названия. Проверяются выступ и левая табуляция.
Номер начинается с 1,25 см; для обычного номера вида `1.1` текст начинается
с 2,25 см. Для широких номеров/шрифтов позиция текста увеличивается.
Этот технический запас места не является новым числовым требованием СТП.
Общие стили и определения нумерации сохраняются. Если номер набран вручную,
его разделитель заменяется табуляцией. При автоматическом номере с суффиксом
«пробел»/«нет» перед названием добавляется табуляция; при суффиксе «табуляция»
используется существующий механизм номера. Слова названия, номера, переносы и
начертания сохраняются. Проверка сохранённой копии разрешает только это
конкретное изменение пробельного разделителя; изменение слов приводит к ошибке.
Отступы в знаках, поля и неоднозначные конструкции остаются для ручной проверки.

В F07 промежуток «заголовок → пустой абзац → следующий блок» исправляется
как одна операция. Пустому абзацу задаются интервал 1.0 и «До»/«После» 0 пт;
у заголовка обнуляется только интервал после, у следующего блока — только
интервал до, включая интервалы в строках и автоматические интервалы.
Интервал до заголовка, после следующего блока и межстрочный интервал
этих двух абзацев сохраняются. Общие стили не меняются. Если один из трёх
абзацев защищён или содержит неподдерживаемые изменения Word, операция
пропускается целиком. Пустые абзацы не добавляются и не удаляются;
несколько пустых абзацев, разрывы и структурные границы остаются вручную.

`formal_check.inspect_document()` использует те же правила, что и
`check_document()`, но дополнительно возвращает внутреннюю модель с точными
объектами нарушений. Эти данные используются в памяти одного запуска;
в `locations` есть необязательный текстовый `context` для поиска объекта.
План исправлений на диск не записывается.

`formal_fix` меняет локальные свойства объектов, не переписывает общие стили
и не заменяет текст абзацев. В DOCX заменяется только `word/document.xml`;
содержимое остальных частей архива копируется без изменений, включая медиа,
стили, нумерацию, отношения, колонтитулы и дополнительные части. Копия сначала
сохраняется во временный файл, повторно читается, проверяются целевые свойства,
текст и неизменность номеров и уровней списков,
затем выходной файл заменяется атомарно. Полный повтор всех действующих проверок делает вызывающий
код отдельным вызовом. При сбое до публикации прежний выходной файл сохраняется.
Входной файл нельзя редактировать одновременно с обработкой.

Если доступных операций нет, выходной DOCX всё равно создаётся и побайтово
совпадает с исходным. Повторный запуск на уже исправленном документе также
не меняет его. Успешный код завершения не означает, что все нарушения устранены.
Изменение полей и интервалов может сдвинуть страницы; поля и содержание может
потребоваться обновить в Word. Проверка окончательной вёрстки не выполняется.

## Удобный просмотр замечаний

Готовая страница с отчётами обеих курсовых — `reports/index.html`.
Откройте её двойным щелчком в обычном браузере: сервер и интернет не нужны.
В странице уже находятся все замечания из `reports/1.json` и `reports/2.json`.

Чтобы создать или обновить страницу после повторной проверки:

```bash
.venv/bin/python -m formal_check.viewer reports/1.json reports/2.json \
  --output reports/index.html
```

В странице доступны переключение отчётов, поиск по фрагменту/правилу/пункту СТП,
фильтры статуса и правила, копирование фрагмента для поиска в Word, отметки
«Разобрано», скрытие разобранного и печать текущего набора замечаний.
Новый JSON можно загрузить кнопкой или перетащить в окно; допускается сразу
несколько файлов. Все данные обрабатываются локально в браузере.

Отметки сохраняются в хранилище браузера для конкретной версии отчёта.
Если браузер запрещает сохранение, отметки остаются доступны в открытой вкладке.
После редактирования DOCX повторно выполните проверку и загрузите новый JSON.
Загрузка через кнопку действует в текущей вкладке; для нового самостоятельного
HTML с этими данными снова выполните команду выше.

Без входных файлов команда создаёт пустую страницу для последующей загрузки JSON:

```bash
.venv/bin/python -m formal_check.viewer --output reports/index.html
```

## Использование из Python

```python
import logging
from formal_check import check_document, DocumentReadError, CheckError

logging.basicConfig(level=logging.INFO)  # диагностика отдельно от результата

try:
    report = check_document("docs/1.docx")
except DocumentReadError as exc:
    print(f"Не удалось прочитать документ: {exc}")
except CheckError as exc:
    print(f"Проверка не завершена: {exc}")
else:
    # report — обычный dict, готовый для json.dumps(..., ensure_ascii=False)
    print(len(report["findings"]))
```

Для интеграции достаточно импортировать пакет из корня проекта или добавить его
корень в `PYTHONPATH`. Функция не настраивает обработчики логирования вызывающего
приложения. Диагностика использует логгер `formal_check`; сообщения о покрытии
правил доступны на уровне INFO.

## Формат результата

```json
{
  "standard": "СТП 01–2017",
  "findings": [
    {
      "rule_id": "F03",
      "standard_reference": "2.1.1, приложение Л; исключение заказчика от 21.10.2026",
      "status": "error",
      "locations": [
        {
          "section": "1 Основная часть",
          "fragment_start": "Обычный текст документа.",
          "property": "line_spacing"
        }
      ],
      "actual": "Межстрочный интервал — 1,5.",
      "expected": "В настройках абзаца установите одинарный межстрочный интервал (1,0). Это требование действует по согласованному исключению заказчика от 21.10.2026."
    }
  ]
}
```

`error` — подтверждённое нарушение; `recommendation` — отклонение от рекомендации;
`review` — конкретный фрагмент, требующий решения человека. Техническая
неподдержанность и отложенные части проверок записываются в журнал.

Пояснения во всех правилах оформляются одинаково: `actual` описывает найденное
значение или проблему по-русски, `expected` содержит конкретное действие.
В ручной проверке сначала объясняется, что нужно проверить; рекомендации
сохраняют рекомендательный характер. Размеры указываются в миллиметрах или
пунктах шрифта, дробные значения — с запятой. Например:
«Нижнее поле — 20 мм.» → «Установите нижнее поле 27 мм.»
Названия режимов интервала и выравнивания также выводятся по-русски.

Машинные ключи JSON, идентификаторы правил и `locations.property` предназначены
для интеграций. HTML показывает для свойств русские подписи. Исходный
`fragment_start` сохраняется дословно, включая иностранные слова, чтобы его
можно было найти в Word. В F33 сохраняется одна карточка на источник. Внутри
отдельными строками перечисляются все найденные места, включая несколько
одинаковых разделителей. Для каждого показаны исходный фрагмент, конкретная
проблема и вариант исправления. Например: «Режим доступа: https://example.org» →
«Режим доступа : https://example.org»; требуется только пробел перед двоеточием.
Уже существующие пробелы не предлагается добавлять повторно.

В F33 двойная косая черта `//` считается одним библиографическим разделителем.
Запятая между фамилией и инициалами проверяется только в авторском заголовке
в начале записи; после `/`, например в «под ред. Иванова И. И.», она не требуется.
Пробелы между инициалами проверяются в распознанных именах, вид издания —
по известным полным и сокращённым формам после двоеточия, «Мн.» — только
в области места издания перед двоеточием или запятой. URL, DOI, электронная
почта, пути к файлам, время, числовые отношения, диапазоны и текст в кавычках
или квадратных скобках исключаются из соответствующих проверок. Слитные
одиночные `/` и тире внутри слов неоднозначны и не объявляются ошибками.
Это ограниченные проверки оформления, а не полный разбор ГОСТ 7.1–2003.

Начиная с версии 0.2.0, у каждого замечания обязательно поле
`standard_reference`: строка с конкретными пунктами, приложениями и примечаниями
СТП из столбца «Основание в СТП» для соответствующего `rule_id`. Поле заполняется
для всех статусов: `error`, `recommendation` и `review`. Если правило опирается
на несколько пунктов, приводится весь перечень оснований этого правила.
Например, для F30 указаны пункт 2.7.3 и пояснение ректората; для F01 — `"2.1.2, приложение Л"`.
В F03 явно указано исключение заказчика: интервал 1.0 не приписывается тексту СТП.
В F05 также отмечено уточнение заказчика о настройках отступов заголовка раздела.
В F02/F06/F07/F09/F30/F31 указано пояснение ректората, переданное заказчиком 21.10.2026.
Валидатор проверяет наличие поля и соответствие основания идентификатору правила.
Интеграции, проверяющие точный набор полей, должны учитывать новое поле.

`fragment_start` — дословное начало извлечённого текста, без выдуманного
автоматического номера; в нём могут быть табуляция или явные переводы строки.
Для отдельнострочной формулы используется текст её видимых текстовых элементов,
даже если обычный текст абзаца пуст. Это линейное извлечение, а не точное
изображение дробей, индексов и других математических конструкций.
Необязательный `locations.context` содержит понятный ориентир: цитаты соседнего
текста и позицию объекта между ними. Например: «Формула: позиция 1 после
фрагмента “Коэффициенты вычисляются по формулам:”. Далее следует “Полином имеет
два корня.”». Цитаты берутся из непрерывного текста, без склейки через встроенные
формулы, и не переходят в другой раздел, ячейку или элемент управления содержимым.
Такой контекст также создаётся для пустых абзацев, изображений и пустых ячеек.
Внутренний номер абзаца не используется как единственный ориентир.
Место ячейки содержит номер таблицы из подписи (при его отсутствии — порядковый
номер таблицы Word), строку и столбец исходной сетки. Для секций используется
номер секции DOCX. Номера страниц не вычисляются.
Валидатор отклоняет место, содержащее только `property` без раздела, фрагмента
или контекста, а также пустые и пробельные значения необязательных полей.
Интеграции с точным перечнем ключей `locations` должны разрешать `context`.
Ранее сохранённые отчёты не получают новые ориентиры автоматически: DOCX нужно
проверить заново. Обе HTML-страницы показывают контекст и включают его в поиск.

`{"standard": "СТП 01–2017", "findings": []}` означает отсутствие замечаний
**в пределах выполненных проверок**, а не полное соответствие СТП.

## Устройство модуля

| Файл / каталог | Назначение |
|---|---|
| `formal_check/reader.py`, `model.py` | Чтение DOCX и модель абзацев, таблиц и объектов |
| `formal_check/formatting.py` | Наследование свойств и автоматическая нумерация |
| `formal_check/classify.py` | Области документа, заголовки, код, подписи и назначение таблиц |
| `formal_check/rules/` | Отдельно зарегистрированные действующие правила, сгруппированные по теме |
| `formal_check/report.py` | Контракт JSON, валидация, устранение точных дублей |
| `formal_check/standards.py` | Основания СТП для всех действующих правил |
| `formal_check/messages.py` | Русские названия режимов оформления и формат чисел в пояснениях |
| `formal_check/viewer.py`, `formal_check/templates/report.html` | Самодостаточная HTML-страница с просмотром JSON и рабочими отметками |
| `formal_check/checker.py`, `coverage.py` | API, запуск правил и диагностика ограничений |
| `formal_check/__main__.py` | CLI и атомарная запись |
| `tests/` | Генерация небольших DOCX и приёмочные/регрессионные тесты |

Используются `python-docx`, `lxml` и стандартная библиотека. Обход XML сохраняет
порядок абзацев и таблиц, содержимое `w:sdt`, текст гиперссылок, сохранённые
результаты полей, вложенные таблицы и исходную сетку объединённых ячеек. Инструкции
полей не попадают в обычный текст. Читаются связанные колонтитулы и реальные сноски.

Для используемых свойств разрешаются `docDefaults`, цепочки `basedOn`, стили
абзаца/символов, прямое оформление, свойства уровня нумерации, `allCaps` и
переключаемые свойства начертания. Порядок применения свойств опирается на
[иерархию OOXML в документации Microsoft](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.paragraphstyleid?view=openxml-3.0.1).
Поддержаны распространённые десятичные и буквенные номера, шаблоны `%1…%9`,
перезапуски, `lvlOverride`, связи стилей с уровнями и `numStyleLink`. Значения
размеров сравниваются с допуском в один twip, где требуется округление.

Правила зафиксированы в коде. Markdown при запуске не разбирается. При неизменном
файле, коде правил и зависимостях порядок и содержание JSON воспроизводимы.

## Существенные ограничения

- Это анализ структуры DOCX, не движок вёрстки Word. `lastRenderedPageBreak`,
  сохранённые номера TOC и заданный разрыв не доказывают реальное начало страницы.
- Разделение областей и назначения объектов эвристическое. Нет универсального
  надёжного способа отличить код, формулу обычным текстом, задание или служебную
  таблицу по одному внешнему виду. Возможны пропуски и адресные замечания review.
- Отсутствие OMML/таблиц Word не доказывает отсутствия формул/таблиц на изображениях.
  OCR, старые редакторы формул OLE, содержимое рисунков, плавающие текстовые блоки,
  `altChunk` не анализируются; ограничения записываются в журнал.
- Используется итоговый текст исправлений: вставки включаются, удаления исключаются.
  История правок, скрытый текст, комментарии рецензента не проверяются как основной текст.
- Поддержана распространённая часть каскада оформления. Полная условная стилизация
  таблиц, редкие форматы автоматических номеров, зависимые от языка подстановки
  шрифтов темы, печатная раскладка сетки документа не реализованы.
- Файлы `.doc`, PDF, DOCX с макросами и архивы с суммарным распакованным размером
  свыше 256 МиБ не поддерживаются. Чтение повреждённого файла — ошибка, а не пустой отчёт.
- Два исходных документа используются как реальные примеры с ошибками.
  Их отчёты не являются заранее заданными эталонами.

## Проверка

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest tests -q
```

Тесты создают небольшие DOCX во временном каталоге: корректный документ, неверные
поля/интервалы, отступы и выравнивание заголовков, обязательное полужирное
начертание, текст по ширине, ненумерованные названия и промежутки после них,
отмену нумерации и сохранение явных отступов, продолжения предложений после формул и новые абзацы,
пунктуацию формул внутри и вне редактируемых выражений, границы областей, наследование, allCaps,
автоматические номера/перезапуски, SDT,
гиперссылки/поля, формулы и их группы, таблицы с объединениями, приложения,
библиография, сноски и примечания. Проверяются разделение error/recommendation/review,
валидность JSON, отказ при сбое, CLI, воспроизводимость и неизменность обеих курсовых.

Проверено 22.10.2026: **566 тестов основного модуля и 6 тестов прототипа прошли**.
Проверки автоисправления охватывают:
точная адресация одинаковых фрагментов, наследование, исключения после формул,
сохранность содержимого и частей DOCX, повторный запуск, CLI и обработка сбоев.
Отдельно проверены отступы F05 при ручной и автоматической нумерации, связь
нумерации со стилем и сохранение идентификатора, уровня и отображаемых номеров.
Обе команды CLI выполнены на предоставленных курсовых; результаты находятся в
`reports/1.json`, `reports/2.json`, диагностика — в одноимённых `.log`.
В первой курсовой найдены нижние поля 20 мм вместо 27 мм и отсутствие статуса
приложения Б. F03 проверяет одинарный интервал 1.0;
правое поле 20 мм нарушением не считается. F06 дополнительно проверяет
выравнивание обычного текста по ширине и оформление заголовков по пояснению ректората.
Воспроизводимость отчётов и неизменность исходных DOCX проверяются тестами.
Набор ошибок в курсовых не зафиксирован в тестах: документы можно исправлять.

CLI автоисправления также выполнен на обеих курсовых. Копии сохранены как

Второй запуск не изменил полученные файлы. Автоматически проверены структура
и содержимое DOCX; окончательная раскладка страниц в Word не проверялась.
