# Инструкции для дальнейшей разработки

## С чего начать

Перед изменениями прочитайте:

1. `docs/PROJECT.md` — назначение, архитектура и принятые решения.
2. `docs/FRONTEND.md` — контракт API и требования к будущему интерфейсу.
3. `BACKEND.md` — запуск, настройки и примеры HTTP-запросов.

Текущий проект — работающий FastAPI-бэкенд и адаптивный интерфейс NormaCheck
в `frontend/` (HTML, CSS, JavaScript-модули без сборки). FastAPI отдаёт `/`
и `/assets/` с того же origin, что и API. Не публикуйте проект и не настраивайте внешний сервер без задачи
на публикацию.

## Решения, которые нужно сохранять

- MVP проверяет оформление DOCX по одной редакции СТП 01–2017 с уточнениями
  заказчика. Смыслового анализа, LLM, OCR и рендеринга страниц пока нет.
- Базы данных нет. Исходники, исправленные копии, JSON-отчёты и метаданные
  хранятся в одном основном каталоге `storage/documents/<uuid>/`.
- Все принятые документы сохраняются постоянно для последующей аналитики.
  Не добавляйте удаление документов в API или UI, TTL, очистку по возрасту,
  удаление при сбое, автоматическое удаление старых файлов при заполнении диска.
  Служебные временные файлы обработки можно очищать, не затрагивая исходники
  и опубликованные результаты. `storage/` не является тестовой папкой.
- Данные остаются закрытыми: проверка владельца выполняется на сервере по
  подписанной HttpOnly-cookie. `document_id` сам по себе не даёт доступа.
  Не открывайте `storage/` как статику и не передавайте браузеру `owner_id`,
  секреты, внутренние пути или XML-объекты документа.
- Разные документы должны обрабатываться параллельно. Один процесс Uvicorn
  координирует несколько дочерних обработчиков; параллельность регулируется
  `MAX_CONCURRENT_JOBS`. Не сводите приложение к одной глобальной обработке.
- Исходный DOCX неизменен. Исправление создаёт отдельный файл и обязательно
  завершается полной повторной проверкой перед разрешением скачивания.
- Точные объекты исправления заново получает `formal_fix` через
  `inspect_document`. Не исправляйте документ по присланным браузером фрагментам,
  публичному JSON или предполагаемым номерам страниц.
- Сохраняйте различие `error`, `review`, `recommendation`. Пустой отчёт означает
  отсутствие замечаний в пределах выполненных проверок, а не полное соответствие СТП.
- Контракт публичного `report` строгий: дополнительные поля приложения
  располагаются рядом с `report`, а не внутри него.

## Работа над фронтендом

Для текущего API используйте относительные `/api/...` и один origin;
для отдельного dev-сервера настройте прокси к FastAPI. CORS сейчас не настроен.
У API нет очереди с `202`, WebSocket, серверного списка загрузок, удаления,
скачивания исходника, `can_fix` у каждого замечания или точного числа исправлений.
Не проектируйте интерфейс так, будто эти возможности уже существуют.

Начинайте с реального API: сессия → загрузка → отчёт → исправление → новый
отчёт → скачивание. Не подменяйте рабочую интеграцию демонстрационными данными.
Изменения API, необходимые фронтенду, делайте явно и отражайте в документации.
Не меняйте формальные нормы и код модулей оформления ради удобства интерфейса.

## Проверки и документация

- Python бэкенда: 3.12. Runtime-зависимости фиксирует `requirements.lock`.
- Запуск: `.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1`.
- Интеграционные тесты: `.venv/bin/python -m pytest tests -q`.
- Для тестов генерируйте DOCX во временном каталоге, не используйте и не
  удаляйте пользовательские документы из `storage/`.
- После изменения поведения обновляйте `docs/PROJECT.md`, `docs/FRONTEND.md`
  и/или `BACKEND.md` в затронутой части. При расхождении сначала проверьте код
  и явные требования пользователя; документация не заменяет проверку реализации.
- Длинный `README.md` содержит историю исходных модулей и ссылки на отсутствующие
  материалы. Не считайте эти материалы доступными без проверки файлов.
