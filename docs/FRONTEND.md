# Контракт для разработки фронтенда

Состояние: 24.10.2026. Ниже описано фактическое API из `app/routes.py`,
`app/service.py`, `app/security.py` и `formal_check/report.py`.
Интерфейс реализован в `frontend/`; ниже также описан его контракт интеграции. Архитектура — в
[PROJECT.md](PROJECT.md), запуск API — в [BACKEND.md](../BACKEND.md).

## Целевой пользовательский сценарий

1. Открыть интерфейс, установить сессию через `GET /api/session`.
2. Выбрать один DOCX и отправить в `POST /api/documents`.
3. Дождаться проверки, сохранить `document_id`, показать исходный отчёт.
4. По нажатию «Автоисправление» вызвать `/fix` для этого UUID.
5. Дождаться повторной проверки и заменить отображаемый отчёт новым.
6. Показать скачивание по `download_url`, объяснить оставшиеся замечания.
7. После ручных исправлений в Word пользователь загружает DOCX заново.

Все принятые документы остаются на сервере для аналитики. Кнопки удаления,
удаления через API и ограничения срока хранения нет. Удалить запись из
локального списка интерфейса, если это понадобится, можно только с ясной
подписью «Скрыть из списка»; это не удаление серверных файлов.

Интерфейс NormaCheck использует HTML, CSS и JavaScript-модули без сборки, npm-зависимостей
и CDN. Светлый адаптивный дизайн, зелёный акцент; регистрация, редактор DOCX,
LLM и аналитический кабинет не добавлены.

## Подключение и origin

Приложение по умолчанию запускается на `http://127.0.0.1:8000`. `/` отдаёт
`frontend/index.html`, `/assets/` — только файлы из `frontend/assets/`.
CORS не включён; `/openapi.json` содержит схему API;
`/docs` и `/redoc` отключены.

Реализованная интеграция — относительные `/api/...` с того же origin, что и
страница. В разработке отдельный dev-сервер фронта может проксировать `/api`
к FastAPI. Пример, только если выбран Vite:

```js
// Фрагмент будущего vite.config.js, сейчас такого файла в проекте нет.
export default {
  server: {
    proxy: {
      "/api": { target: "http://127.0.0.1:8000", changeOrigin: true },
      "/health": { target: "http://127.0.0.1:8000", changeOrigin: true }
    }
  }
};
```

Оба `localhost` и `127.0.0.1` допустимы для API, но не смешивайте их в браузере:
это разные cookie-хосты. Используйте один адрес фронта на протяжении сессии.
`ALLOWED_HOSTS` — проверка Host, она не заменяет CORS.

Прямые браузерные запросы с другого origin требуют отдельного изменения CORS
и проверки cookie-политики. Одного `credentials: "include"` для этого недостаточно.
Не используйте `mode: "no-cors"` и не отключайте проверку владельца или CSRF.

HTML отдаётся самим FastAPI через текущий middleware,
на него распространяется CSP `script-src 'self'; style-src 'self'`:
inline-скрипты, inline-стили и внешние CDN не разрешены этой политикой.
Все стили и скрипты лежат в локальных внешних файлах. HTML получает
`Cache-Control: no-cache`, API по-прежнему получает `no-store`.

## Сессия и авторизация

`GET /api/session` без тела и специальных заголовков возвращает 200:

```json
{
  "csrf_token": "строка-токен",
  "max_upload_bytes": 20971520,
  "max_concurrent_jobs": 2,
  "retention_hours": null
}
```

Числа — значения по умолчанию, а не константы интерфейса. Лимит размера берите
из ответа. `retention_hours: null` означает постоянное хранение.

В ответе устанавливается `docx_session`: подписанная HttpOnly-cookie,
`SameSite=Lax`, путь `/`, срок 7 суток. Она не содержит пароль и не является
регистрацией пользователя. Cookie проверяет бэкенд; читать её через JavaScript,
хранить в localStorage или отправлять `owner_id` не нужно.

Храните CSRF-токен в памяти приложения. При инициализации страницы получите
его заново через `/api/session`. POST-запросы требуют `X-CSRF-Token` и cookie;
GET отчёта и скачивания требуют cookie, но не CSRF.

Вызов `/api/session` с действующей cookie сохраняет того же владельца и
обновляет срок cookie. Если cookie пропала или истекла, создаётся новый владелец.
Новая сессия не получает права на старые UUID. Серверные файлы при этом остаются.
Смена `APP_SECRET` тоже делает старые cookie недействительными.

В локальном HTTP-режиме `COOKIE_SECURE=false`; настройка `true` предназначена
для HTTPS. Не меняйте секрет на каждый запуск фронта и не генерируйте сессию
отдельно для каждого документа.

## Эндпоинты

| Метод | Путь | Успех | Тело запроса |
| --- | --- | --- | --- |
| GET | `/api/session` | 200, настройки и CSRF | Нет |
| POST | `/api/documents` | 201, `DocumentResponse` | Multipart: ровно один `file` |
| GET | `/api/documents/{id}` | 200, `DocumentResponse` | Нет |
| POST | `/api/documents/{id}/fix` | 200, `DocumentResponse` | Нет |
| GET | `/api/documents/{id}/download` | 200, DOCX | Нет |
| GET | `/health` | 200, `{"status":"ok"}` | Нет |

`POST /api/documents` принимает ровно один файл и не принимает дополнительных
полей формы. Для `FormData` не устанавливайте `Content-Type` вручную:
браузер добавляет multipart boundary. `accept=".docx"` и проверка размера
в браузере полезны, но серверная валидация остаётся обязательной.

Для нескольких файлов отправляйте отдельные запросы и учитывайте
`max_concurrent_jobs`. Не посылайте несколько файлов в одном multipart.
UI может вести несколько операций независимо; блокируйте повторную операцию
конкретного документа, а не работу всех документов одним общим флагом.

POST ожидает весь результат. Нет `202`, отдельного job ID, очереди,
WebSocket/SSE или точного процента проверки. Показывайте неопределённый индикатор
«Проверяем документ» / «Исправляем и повторно проверяем».

## Типы ответа

Ниже типы для описания контракта; они не обязывают выбирать TypeScript.

```ts
type FindingStatus = "error" | "review" | "recommendation";
type DocumentState = "checking" | "checked" | "fixing" | "fixed" | "failed";
type DocumentVersion = "original" | "corrected" | null;

type FindingLocation = {
  section: string;
  fragment_start?: string;
  property?: string;
  context?: string;
};

type Finding = {
  rule_id: string;
  standard_reference: string;
  status: FindingStatus;
  locations: FindingLocation[];
  actual: string;
  expected: string;
};

type FormalReport = {
  standard: "СТП 01–2017";
  findings: Finding[];
};

type DocumentResponse = {
  document_id: string;
  filename: string;
  state: DocumentState;
  current_version: DocumentVersion;
  created_at: string; // ISO 8601, дата с UTC-offset
  expires_at: null;
  checker_version: string;
  ruleset_version: string;
  last_error: { code: string; message: string } | null;
  report: FormalReport | null;
  warnings: string[];
  limitations: { rule_id: string; description: string }[];
  download_url: string | null;
};
```

Успешные загрузка, исправление и чтение возвращают одну форму `DocumentResponse`.
Пример сокращённого ответа проверки; пустые `warnings` и `limitations` здесь
показаны для краткости, в реальном ответе `limitations` содержит описание правил:

```json
{
  "document_id": "11111111-1111-4111-8111-111111111111",
  "filename": "Курсовая.docx",
  "state": "checked",
  "current_version": "original",
  "created_at": "2026-10-24T10:00:00+00:00",
  "expires_at": null,
  "checker_version": "0.3.5",
  "ruleset_version": "stp-01-2017-2026-10-22",
  "last_error": null,
  "report": {
    "standard": "СТП 01–2017",
    "findings": [
      {
        "rule_id": "F03",
        "standard_reference": "2.1.1, приложение Л; исключение заказчика от 21.10.2026",
        "status": "error",
        "locations": [
          {
            "section": "1 Основная часть",
            "fragment_start": "Система выполняет проверку документации.",
            "property": "line_spacing"
          }
        ],
        "actual": "Межстрочный интервал — 1,5.",
        "expected": "Установите одинарный межстрочный интервал (1,0)."
      }
    ]
  },
  "warnings": [],
  "limitations": [],
  "download_url": null
}
```

Для исправленной версии `current_version="corrected"`, обычно `state="fixed"`,
а `download_url` имеет вид `/api/documents/<id>/download`. У исправленной копии
остаётся тот же `document_id`; её исходное пользовательское имя в `filename`
не меняется. Итоговое имя скачивания задаёт `Content-Disposition`.

## Как показывать отчёт

Карточка замечания содержит:

- статус: «Ошибка», «Ручная проверка», «Рекомендация»;
- идентификатор правила и полное `standard_reference`;
- все элементы `locations` с фрагментом, контекстом и разделом, если они есть;
- `actual` как описание найденной проблемы и `expected` как требуемое действие.

`section` может быть пустой строкой. `fragment_start`, `context`, `property`
необязательны. Например, у параметров секции может не быть обычного текстового
фрагмента. Не скрывайте такое замечание и не считайте его повреждённым.
Номер страницы, координаты в предпросмотре, стабильный ID конкретного замечания
или XPath в API отсутствуют.

`fragment_start` сохраняйте дословно, включая пробелы, табуляцию и переводы
строк: это ориентир для поиска в Word. Полезна кнопка копирования фрагмента.
Машинные `property` можно переводить в подписи через словарь, сохраняя запасной
вариант для неизвестных свойств. На незнакомом ключе интерфейс не должен падать.

Все строки документа и отчёта — недоверенный текст. Выводите их через
экранирование фреймворка или `textContent`, сохраняйте переносы (`pre-wrap`).
Не используйте `innerHTML` или автоматический HTML/Markdown-рендеринг.
`standard_reference` — текст основания, а не готовая ссылка на файл стандарта.

Показывайте три отдельных счётчика статусов, поиск и фильтры по статусу и правилу.
Счётчик карточек равен числу элементов `findings`, а не числу XML-объектов,
мест в `locations`, изменённых свойств или выполненных исправлений.
ID правил имеют пропуски и не образуют непрерывные F01–F36.

`warnings` описывают особенности конкретного документа. `limitations` содержат
границы реализованных проверок и должны быть доступны пользователю отдельно
от замечаний. Они не являются ни нарушениями, ни подтверждением успешной проверки.

Пустой `findings` показывайте как «В пределах выполненных проверок замечаний
не найдено». Не обещайте полное соответствие СТП. Если `report=null`, проверка
не дала доступного отчёта; это не успешный результат с нулём ошибок.

## Состояния интерфейса

| Серверное состояние | Что показывать | Действия |
| --- | --- | --- |
| `checking` | Проверка ещё идёт; отчёта может не быть | Ожидать ответ/опрашивать известный UUID |
| `checked` | Исходный отчёт | Автоисправление при `current_version="original"` |
| `fixing` | Исправление и повторная проверка; прежний отчёт доступен | Заблокировать повторное исправление этого UUID |
| `fixed` | Отчёт исправленной копии | Скачивание по непустому `download_url` |
| `failed` | `last_error` и последний доступный отчёт, если есть | Повторить `/fix`, если осталась исходная проверенная версия; иначе предложить новую загрузку |

Основной отчёт всегда берите из последнего ответа API. После `/fix` не удаляйте
карточки предположительно исправленных правил локально и не используйте старый
отчёт как результат новой проверки. Часть нарушений F04–F07 может остаться.

Если страница открылась с известным UUID в состоянии `checking` или `fixing`,
можно опрашивать GET раз в 1–2 секунды и прекращать опрос при завершении/ошибке.
При начальной загрузке UUID ещё не известен до ответа 201 — опрашивать нечего.
На ошибку исправления полезно один раз получить GET известного UUID, чтобы
показать актуальный статус и сохранившийся исходный отчёт.

Не определяйте доступность скачивания только по счётчику ошибок или наличию
файла: ориентируйтесь на `download_url`. Нулевые ошибки для скачивания не требуются.
Для сообщения о завершении достаточно «Поддерживаемые исправления применены;
ниже актуальный отчёт». API не даёт точного числа выполненных операций.

Если исправлять нечего, сервер всё равно возвращает проверенную копию.
Публичного признака `can_fix` для каждой карточки нет. Не рисуйте индивидуальные
кнопки исправления, исходя только из `rule_id`. Общий `/fix` сам выбирает
безопасные операции; `review` и `recommendation` автоматически не исправляются.

## Ошибки и повторные запросы

Основной формат ошибки:

```json
{
  "error": {
    "code": "busy",
    "message": "Все обработчики заняты. Повторите попытку немного позже."
  }
}
```

| HTTP | Частые `error.code` | Поведение интерфейса |
| --- | --- | --- |
| 400 | `request_error` | Проверить multipart; неверный Host может вернуть обычный текст |
| 401 | `session_required` | Установить сессию; потерянный доступ к прежним UUID не восстанавливается автоматически |
| 403 | `csrf` | Обновить сессию/токен; не повторять изменяющий запрос бесконечно |
| 404 | `not_found` | Документ не существует или не принадлежит сессии; не показывать чужие данные |
| 405 | `request_error` | Такого метода нет; удаление не поддерживается |
| 408 | `request_error` | Истекло время чтения очередной части запроса |
| 409 | `document_busy`, `not_checked`, `not_ready` | Уточнить состояние известного UUID |
| 413 | `file_too_large` или `request_error` | Показать допустимый размер файла |
| 415 | `unsupported_format` | Нужен DOCX |
| 422 | `missing_file`, `empty_file`, `invalid_document` | Объяснить проблему входа и предложить другой файл |
| 500 | `processing_failed`, `worker_failed`, `internal_error` | Не подменять ошибку пустым отчётом; сохранить предыдущий отчёт в UI |
| 503 | `busy` | Учесть `Retry-After: 5`, предложить повторить позже |
| 504 | `timeout` | Сообщить о тайм-ауте обработки |
| 507 | `storage_full` | Место закончилось; не предлагать пользователю удалить серверные документы |

Не все ответы имеют основной формат: ранние ошибки middleware могут быть
`{"detail":"..."}`, а `TrustedHostMiddleware` возвращает текст. Сначала
проверяйте HTTP-статус; обработчик ошибок должен переживать не-JSON ответ.

Не включайте автоматический повтор загрузки при любом сетевом сбое: повторный
POST создаёт новую постоянную загрузку. Обрыв сети или отмена ожидания браузером
не доказывают, что сервер не принял документ. API не поддерживает idempotency key
и не возвращает UUID в стандартном теле ошибки начальной загрузки.
`/fix` после успеха возвращает готовую копию; при незавершённой операции может
вернуть 409. Для этой операции сначала уточняйте состояние UUID.

## Минимальный клиент API

Пример обычного JavaScript, без привязки к фреймворку. Скачивание выполняется
отдельной ссылкой; приведённый helper предназначен для JSON-эндпоинтов.

```js
let csrfToken = "";

async function jsonRequest(path, init = {}) {
  const headers = new Headers(init.headers);
  if (init.method === "POST") headers.set("X-CSRF-Token", csrfToken);
  const response = await fetch(path, {
    ...init,
    headers,
    credentials: "same-origin"
  });
  const text = await response.text();
  let data = null;
  try { data = JSON.parse(text); } catch { /* Допустим не-JSON ответ ошибки. */ }
  if (!response.ok) {
    const detail = typeof data?.detail === "string" ? data.detail : null;
    const error = new Error(data?.error?.message || detail || `Ошибка HTTP ${response.status}`);
    error.status = response.status;
    error.code = data?.error?.code || "http_error";
    error.retryAfter = response.headers.get("Retry-After");
    throw error;
  }
  if (data === null) throw new Error("Сервер не вернул ожидаемый JSON.");
  return data;
}

async function initializeSession() {
  const session = await jsonRequest("/api/session");
  csrfToken = session.csrf_token;
  return session;
}

async function uploadDocument(file) {
  const form = new FormData();
  form.append("file", file, file.name);
  return jsonRequest("/api/documents", { method: "POST", body: form });
}

function getDocument(id) {
  return jsonRequest(`/api/documents/${encodeURIComponent(id)}`);
}

function fixDocument(id) {
  return jsonRequest(`/api/documents/${encodeURIComponent(id)}/fix`, { method: "POST" });
}

// Перед uploadDocument/fixDocument нужно дождаться initializeSession().
// Для скачивания: обычная <a href={response.download_url}> с того же origin.
```

Cookie обычной ссылки скачивания отправится автоматически. Тип файла:
`application/vnd.openxmlformats-officedocument.wordprocessingml.document`.
`Content-Disposition` задаёт `filename*=UTF-8''...` для имени с кириллицей
и запасное `filename=corrected.docx`.

## Ручные отметки, восстановление страницы и локальная история

UUID выбранного документа хранится в `?document=...`. После обновления страницы
сначала устанавливается сессия, затем выполняется GET отчёта. Если известный
документ ещё проверяется или исправляется, GET повторяется раз в 1,8 секунды;
при завершении или ошибке опрос прекращается. Обновить статус можно вручную.
Загрузки автоматически не повторяются. После 401/403 обновляется сессия,
а повтор изменяющего действия остаётся за пользователем. После ошибки исправления
клиент пытается получить актуальный отчёт известного UUID.

Галочка «Исправлено» — ручная заметка пользователя о правке в Word, она не меняет
серверный отчёт, DOCX или счётчики статусов. Отмеченные пункты можно скрыть.
В localStorage сохраняются только индексы отметок; ключ — SHA-256 от UUID,
`current_version`, `checker_version`, `ruleset_version` и точного `report`.
Индексы никогда не переиспользуются с другой версией или изменившимся отчётом.
При недоступном localStorage/хешировании галочки работают в памяти с предупреждением.
Текст замечаний не кешируется в браузерном хранилище; CSRF остаётся в памяти.

Поиск учитывает фактическое и требуемое значения, все места, контекст, фрагменты,
основания, ID и подписи правил. Можно одновременно выбирать статус, категорию
(правило) и скрытие отмеченных. Фрагменты сохраняют исходные пробелы и переносы,
есть копирование. Неизвестные свойства выводятся как текст.

Загрузки в текущей вкладке представлены переключателем, который появляется
только при нескольких документах. Он не является серверной историей и не
сохраняется после обновления страницы; выбранный документ восстанавливается по URL.
Независимые операции используют доступную параллельность из `/api/session`.

У API нет списка всех документов сессии. Локальная история — только список
ранее полученных UUID, а не возможность прочитать все серверные файлы.
UUID не заменяет cookie. Если cookie потеряна, локальные ссылки могут дать 404;
это не означает удаления файлов с сервера. Не придумывайте восстановление
прав на старые файлы по имени, UUID или локальному owner_id.

## Приёмка первого фронтенда

1. Сессия устанавливается перед POST; cookie и CSRF работают с выбранным origin.
2. Реальный DOCX загружается, в UI отображается полученный отчёт, не тестовые данные.
3. Карточки показывают все места, основания, фактическое и требуемое значение;
   работают статусы, поиск, фильтры и копирование фрагмента.
4. Объекты без обычного текста, неизвестные `property` и пустой `section`
   отображаются без падения.
5. Исправление заменяет отчёт актуальным, даёт рабочую ссылку скачивания,
   не обещает исправления всех ошибок и не меняет исходник.
6. После обновления страницы известный UUID открывается в той же сессии.
7. Чужая/потерянная сессия не получает документ; ошибка 404 не интерпретируется
   как удаление постоянных данных.
8. Ошибка проверки или исправления не превращается в сообщение «Ошибок нет».
9. Два разных документа могут обрабатываться независимо; повторный `/fix`
   одного UUID блокируется, заполнение слотов 503 обрабатывается понятно.
10. Обрабатываются размер/формат, 403, 409, 422, 500, 503, 504, 507 и сетевой сбой;
    загрузка не повторяется автоматически с созданием дубликата.
11. Есть доступные пояснения `warnings`/`limitations` и корректное сообщение
    для пустого `findings`; номера страниц не выдумываются.
12. Нет кнопки удаления серверных документов, фиктивного анализа содержания,
    несуществующей регистрации, очереди или точного процента обработки.

Проверять интерфейс следует на сгенерированных тестовых DOCX. Не загружайте
и не удаляйте реальные файлы из `storage/` ради проверки UI.

Автоматические проверки: `.venv/bin/python -m pytest tests -q` и
`node --test tests/frontend.test.mjs` (Node 22+ нужен только для тестов).
Для браузерной проверки можно запустить приложение с отдельным
`STORAGE_DIR=/private/tmp/nkprod-ui-check`, сгенерировать DOCX во временной папке
и пройти сценарий через `/`. Для обычного использования отдельный dev-сервер,
Node и сборка не нужны.
