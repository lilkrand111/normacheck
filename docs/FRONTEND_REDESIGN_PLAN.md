# План переработки фронтенда NormaCheck по макету Forma

Дата плана: 27.10.2026. Реализация завершена: 28.10.2026.
Фактические проверки и ограничения приёмки — в [отчёте](design/verification/README.md).

## 1. Цель и границы работы

Полностью заменить визуальный интерфейс `frontend/` дизайном из
[Forma.fig](design/Forma.fig): лендинг, загрузка, рабочее пространство отчёта,
автоисправление, скачивание, ошибки и адаптивные варианты. Сохранить реальную
интеграцию с FastAPI и существующие гарантии обработки документов.

Документ сохраняет исходный план; реализация этапов ниже находится в `frontend/`.
Публикация сайта, изменение VPS, смысловой анализ, регистрация и расширение
формальных проверок в этот план не входят.

Основания плана:

- [AGENTS.md](../AGENTS.md), [PROJECT.md](PROJECT.md),
  [FRONTEND.md](FRONTEND.md), [BACKEND.md](../BACKEND.md).
- [Дизайнерское ТЗ](design/design.pdf): прочитаны обе страницы, просмотрен рендер.
- `Forma.fig`: просмотрено встроенное превью, локально извлечены дерево слоёв,
  видимость, тексты, размеры, шрифты и заливки. Макет не загружался во внешний сервис.
- Проверен код `frontend/index.html`, `frontend/assets/app.js`, `report.mjs`,
  `styles.css`, обработчиков API, формирования ответа и списка разрешённых
  операций `formal_fix/operations.py:ALLOWED`; изучены существующие тесты.

Встроенное превью `.fig` имеет размер 400 × 193 и не подходит для точной визуальной
приёмки. Для реализации получены полноразмерные экспорты выбранных фреймов;
они сохранены в [references/](design/references/).
Структурное чтение `.fig` не подтверждает работоспособность кликабельного прототипа.
Удалённый из рабочей копии `normacheck-figma-screens.pdf` не использован как источник.

## 2. Что именно переносим из макета

### 2.1. Выбранная основа

Основой считать видимый `NormaCheck Лендинг` (`3384:3705`) и набор рабочих
экранов внутри видимого фрейма `не копия` (`3470:1575`). Это рабочее допущение
по текущей структуре файла, а не утверждение о согласовании версии дизайнером.
Скрытые концепции «Тихая форма», «Легче облака», «Красная линия», скрытые копии
и отдельный `Шаблон2` не смешивать с основным набором.

Лендинг имеет размер 1440 × 6580 и девять разделов:

1. Первый экран: навигация, облачный фон, заголовок «Оформление — без лишнего
   шума», основной выбор DOCX и ссылка на пример замечания.
2. Формат и возможности сервиса.
3. О сервисе: объяснение результата, исходника и границ автоматизации.
4. Что проверяет сервис.
5. Как читать замечание: найденное значение, требование, места и основание.
6. Путь документа от загрузки до проверенной копии.
7. Автоисправление и личные отметки как разные действия.
8. Вопросы и границы проверки.
9. Финальное действие и подвал.

Рабочий отчёт — отдельное представление приложения, а не продолжение длинного
лендинга. На основном экране 1440 × 900 предусмотрены общая сводка, фильтры,
ручной прогресс и три области: список замечаний, подробности выбранного
замечания, действия с копией. В фрейме `3470:3020` размеры этих областей —
354 × 490, 586 × 490 и 340 × 490. Это эталон композиции, а не фиксированные
ограничения для текста или всех размеров окна.

### 2.3. Визуальная система

Перенести облачные фоны, светлые поверхности, округления, декоративные карточки,
голубые и лаймовые акценты, типографику и плотность рабочего отчёта.
Сначала составить реестр токенов по конкретным слоям, затем использовать их в CSS.

Извлечённые ориентиры, требующие сверки с полноразмерным экспортом:

| Область | Значения из слоёв |
| --- | --- |
| Лендинг: текст, вторичный текст | `#142128`, `#65747D` |
| Лендинг: акценты | `#087FCC`, `#086EAD`, `#D0FA69` |
| Лендинг: поверхности и линии | `#FFFFFF`, `#F4F6F7`, `#DDE5E9` |
| Рабочие экраны: текст, вторичный текст | `#19201E`, `#66716C` |
| Рабочие экраны: отдельные акценты | `#A34935`, `#88641B`, `#CEF46A` |
| Шрифты | Inter Regular / Medium / Semi Bold; в рабочих экранах также Work Sans Regular |
| Основные размеры | Лендинг 1440; рабочий экран 1440 × 900; узкий отчёт 1120 × 900 |

Не назначать семантику цветов только по частоте встречаемости: проверить,
какие заливки относятся к кнопкам, статусам, фону и декоративным объектам.
Сохранить различия лендинга и рабочего пространства через общие и локальные токены.
Проверить кириллицу, лицензии и доступность файлов шрифтов; загружать их локально
в WOFF2. Отсутствующий шрифт или неподходящую кириллицу зафиксировать как
отклонение, а не скрывать случайной системной заменой.

## 3. Расхождения макета с действующим продуктом

Визуальную композицию переносим из макета. Данные, нормы, разрешённые действия
и обещания пользователю определяются действующим кодом и требованиями проекта.

| Место | Расхождение | Решение для реализации |
| --- | --- | --- |
| Примеры замечаний | Есть `M01`, `M02`, `R01`; в других вариантах есть ошибочные соответствия F-кодов | Рабочий отчёт получает ID и статусы только из API. Названия — из проверенного словаря с запасным вариантом для неизвестного ID |
| Экран 05 | «Автоисправлены F01, F02, F03»; шрифты F02 исправитель не меняет | «Поддерживаемые исправления применены. Копия повторно проверена». Не перечислять выполненные операции: API их не возвращает |
| Экран 05 | «Поддерживаемых правок больше нет» | Заменить на «Копия уже обработана». Оставшиеся замечания не доказывают исчерпания исправляемых свойств |
| Имя исправленной копии | Макет показывает новое имя в заголовке | В ответе `filename` остаётся исходным. Версию обозначать отдельной подписью; имя скачивания получать из `Content-Disposition` |
| Экраны 02 и 04 | Заблокированы смена документа и предыдущий отчёт | Блокировать повторную операцию текущего документа. Просмотр сохранённого отчёта и работа с другими документами остаются доступны в пределах лимитов |
| Стандарт | Элемент похож на выбор редакции | Показывать фиксированный «СТП 01–2017», без несуществующего выбора профилей |
| Категории | Макет содержит укрупнённые группы; сейчас фильтр работает по правилу | На первом выпуске сохранить точную фильтрацию по правилу в новом оформлении. Значения — `F03 · Межстрочный интервал` и т. п.; это явное отличие наполнения от макета, без нового поля API |
| Список из 40 замечаний | Подпись «1–8 из 40» выглядит как страница выдачи | Использовать прокручиваемый список всех подходящих результатов; подпись «Показано N из M». Серверную пагинацию не добавлять |
| Экран 06 | При нуле замечаний убрано действие создания копии | Не выводить из нуля карточек `can_fix`. Сохранить возможность получить проверенную копию через общий `/fix`, с честной подписью без обещания новых исправлений |
| Экран 14 | «Документ недоступен» объясняется невозможностью прочитать выбранный DOCX | Разделить 404/потерю доступа и 422/невалидный DOCX. Потерянная сессия не означает удаления файла |
| Ошибка сети | Простой призыв повторить проверку | Уточнять, что документ мог сохраниться; повтор создаст ещё одну постоянную загрузку. Повтор только по действию пользователя |
| Пример F03 на лендинге | В декоративной карточке основание сокращено | Сохранить уточнение заказчика об одинарном интервале; не выдавать его за дословную норму СТП |
| Хранение документов | В основных экранах макета недостаточно пояснений | Сохранить заметное сообщение о постоянном хранении принятых документов для аналитики и неизменности исходника |

Демонстрационное замечание на лендинге допустимо только как явно подписанный
«Пример замечания». Оно не должно попадать в рабочие отчёты, их счётчики,
автоисправление или скачивание. Кнопки внутри иллюстраций не должны выглядеть
как доступная операция над ещё не загруженным документом.

## 4. Техническое решение

### 4.1. Сохранить лёгкий фронтенд без сборки

Оставить HTML, CSS и JavaScript-модули. React, Vite, отдельный сервер фронтенда,
база данных и новые runtime-зависимости для этой переработки не нужны.
FastAPI продолжает отдавать `/`, `/assets/` и относительные `/api/...` с одного origin.
Новые API-эндпоинты и изменение контракта `report` для запланированного интерфейса
не требуются. `formal_check`, `formal_fix`, хранение и настройки процессов не менять.

Предлагаемая структура после необходимого разделения текущего `app.js`:

```text
frontend/
  index.html                 # Семантический каркас лендинга и приложения
  assets/
    app.js                   # Инициализация, навигация, связывание действий
    api.mjs                  # Сессия, запросы, CSRF, скачивание
    documents.mjs            # Документы вкладки, операции, опрос, общая пауза
    report.mjs               # Поиск, статусы, названия правил, ключи отметок
    views.mjs                # Отрисовка загрузки, списка, деталей и действий
    styles.css               # Общие токены и базовые компоненты
    landing.css              # Разделы лендинга
    workspace.css            # Загрузка, отчёт, адаптивность
    fonts/                   # Только используемые локальные начертания
    images/                  # Оптимизированные ассеты выбранного дизайна
    icons/                   # Локальные SVG-иконки
```

Это целевая декомпозиция, а не требование создать все файлы до первой вёрстки.
Выносить код по мере появления ясной ответственности; `report.mjs` и проверенную
логику запросов переиспользовать. Не переносить весь экспорт Figma в публичную папку.

### 4.2. Навигация и состояние

- `/` показывает лендинг; `/#check` — рабочую загрузку. Якоря лендинга ведут к
  соответствующим разделам. `/?document=<uuid>` сохраняет существующее открытие
  отчёта, после получения сессии выполняется GET документа.
- Переходы внутри приложения не перезагружают страницу и не уничтожают операции
  других документов. Обработать «Назад/Вперёд» и прямое открытие существующего URL.
- Выбор файла и запуск проверки разделить. `selectedFile` хранится только в памяти;
  выбор и drag-and-drop не отправляют POST. «Сменить» меняет локальный выбор до
  отправки и не удаляет серверные документы. После перезагрузки файл выбирают заново.
- Документы текущей вкладки продолжают жить в `Map`; небольшой переключатель
  показывается при нескольких документах. Это дополнение к макету, необходимое
  для сохранения независимых операций, без обещания постоянной истории.
- Для документа хранить выбранный индекс замечания, состояние раскрытия мест
  и фильтры отдельно от ответа API. Индекс относится к исходному массиву
  `findings`, а не позиции в отфильтрованном списке; `rule_id` не уникален.
- После смены отчёта переопределять выбор и раскрытия, загружать отметки по
  существующему SHA-256-ключу. Старые отметки не переносятся; сохранённые отметки
  того же самого отчёта восстанавливаются при повторном открытии.
- При фильтрации сохранять выбранное замечание, пока оно видно. Если оно исчезло,
  выбирать первое подходящее; если список пуст — убирать старые подробности.
- Пока выполняется `/fix`, прежний отчёт доступен с подписью «Предыдущий отчёт».
  Разрешить чтение, поиск и копирование; изменение ручных отметок этого отчёта
  временно отключить. При сбое вернуть редактирование сохранённых отметок.

### 4.3. Список и подробности

Слева показывать компактные строки с категорией, кодом, статусом и ручной отметкой.
По выбору строки центр показывает `actual`, `expected`, все `locations` и полное
`standard_reference`. Одно замечание может иметь несколько мест; раскрытие
«Ещё N мест» не должно терять элементы и доступно с клавиатуры.

Строки отчёта выводить через `textContent`. Фрагменты сохранять дословно,
с пробелами и переносами; копировать оригинальную строку без декоративных кавычек.
Для отсутствующего фрагмента показывать доступный раздел/параметр/контекст,
не рисовать пустую кнопку копирования. Неизвестные свойства и правила не ломают UI.

Различать четыре случая: `report=null`, пустой `findings`, отсутствие совпадений
по фильтрам, совпадения, полностью скрытые ручными отметками. Последний случай
определять сравнением выборки до и после `hideDone`, а не количеством всех отметок.
Общие счётчики всегда вычислять из полного серверного `findings`.

### 4.4. Адаптивность и доступность

- На широком экране — три колонки по основному макету.
- На 1120 px — список и подробности рядом, действия отдельным блоком по узкому
  фрейму. На промежуточных ширинах не допускать сжатия текста до нечитаемости.
- На телефоне — одна колонка: сводка, фильтры, список; подробности выбранного
  замечания раскрываются непосредственно под выбранной строкой. Действия с копией
  доступны отдельным блоком, без горизонтальной прокрутки и скрытых кнопок.
- Не фиксировать высоту всего приложения в 900 px. На большом экране допустима
  отдельная прокрутка списка и деталей; на телефоне — обычная прокрутка страницы.
- Сохранить все действия при 200% масштабе, длинных именах и длинных текстах.
  Мелкие подписи 10–11 px из макета проверить на читаемость и при необходимости
  увеличить, зафиксировав отличие от эталона.
- Семантические кнопки, подписи полей, видимый фокус, доступные имена и порядок Tab.
  Для выбора замечаний достаточно списка кнопок с обозначением текущего пункта;
  сложную имитацию `listbox` без необходимости не вводить.
- Состояния ожидания и ошибки объявлять через подходящие live-region; не озвучивать
  весь отчёт заново при каждом обновлении. После пользовательского перехода
  перемещать фокус предсказуемо, после фонового опроса — не перехватывать его.
- Учитывать `prefers-reduced-motion`; декор не должен мешать чтению и нажатию.

### 4.5. Сеть, безопасность и ресурсы

Сохранить HttpOnly-cookie, CSRF в памяти, проверку владельца на сервере,
не-JSON ошибки и общую паузу POST после 429/503. В течение паузы можно выбрать
файл локально, но запуск запрещён; это намеренное уточнение текущего UI,
где блокируется сам файловый input. Выбор через drop тоже не обходит паузу.

До ответа первоначальной загрузки UUID неизвестен. Не добавлять фиктивный опрос,
очередь, проценты или оставшееся время. Известный UUID можно опрашивать по текущей
схеме; после ошибки `/fix` сначала уточнять состояние, затем предлагать ручной повтор.
Глобально блокировать все документы следует только при реальном общем ограничении,
например Retry-After, а не при любой обработке одного документа.

Скачивание разрешается только по непустому `download_url`. Наличие оставшихся
замечаний этому не мешает. Не обещать сохранение файла на устройство только на
основании клика: после успешного получения файла сообщать «Скачивание началось».

Все CSS, скрипты, изображения и шрифты локальные, с действующей CSP; без CDN,
inline-обработчиков и ослабления политики. Исходники `.fig`, PDF и `storage/`
не публикуются. Облачный декор экспортировать выборочно и оптимизировать;
не превращать весь экран в картинку. Изображения ниже первого экрана грузить
отложенно, задавать размеры, не подключать тяжёлые анимационные библиотеки.
Новый интерфейс не должен увеличивать число процессов на VPS.

## 5. Этапы разработки

### Этап 1. Подготовить эталоны и перечень ассетов

1. Зафиксировать основной набор фреймов из раздела 2 и их полноразмерные экспорты.
2. В Figma или совместимом просмотрщике проверить маски, прозрачности, обрезку,
   порядок слоёв и интерактивные переходы. Если прямого экспорта нет, получить
   экспорты от дизайнера до точной визуальной приёмки; текущего превью недостаточно.
3. Составить перечень фонов, логотипа, иконок и шрифтов; указать исходный слой,
   формат, размер и локальный путь. Подготовить токены цветов, отступов, радиусов,
   теней и типографики. Зафиксировать необходимые мобильные состояния.

**Готово, когда:** разработчик может однозначно сопоставить каждое представление
с эталоном; скрытые концепции исключены, ассеты доступны и понятны отклонения.

### Этап 2. Отделить работающую логику от старой вёрстки

1. Запустить существующие frontend- и backend-тесты как исходную проверку.
2. Вынести API и состояние документов из `app.js`, сохранив поведение запросов,
   опроса, восстановления URL, отметок, скачивания и обработки ошибок.
3. Добавить состояние выбранного файла до отправки и выбранного замечания.
4. Адаптировать тестовый DOM и импорты: нынешний `frontend-ui.test.mjs` загружает
   `app.js` через data URL и переписывает только импорт `report.mjs`. После
   разделения модулей этот механизм потребуется обновить.

**Готово, когда:** существующий реальный цикл работает после выделения модулей;
выбор файла не создаёт загрузку, один запуск создаёт ровно один POST.

### Этап 3. Внедрить визуальную основу и лендинг

1. Подключить локальные ассеты, шрифты и базовые компоненты.
2. Сверстать девять разделов лендинга, навигацию, FAQ и переход к загрузке.
3. Привязать все CTA к рабочему сценарию. «Посмотреть пример» ведёт к явно
   подписанному примеру на лендинге, а не к вымышленному документу в API.
4. Перенести тексты с корректировками раздела 3 и сведениями о хранении.
5. Проверить лендинг на широком экране и телефоне, включая длинные заголовки.

**Готово, когда:** лендинг соответствует выбранной композиции, все ссылки имеют
назначение, с любого CTA можно перейти к реальной загрузке.

### Этап 4. Реализовать загрузку и ожидание

1. Сделать экраны 00–02: выбор, локальная проверка размера/расширения, смена файла,
   ручной запуск, ожидание, ошибки подключения и приёма.
2. Подключить реальный `GET /api/session` и `POST /api/documents`.
3. Сохранить лимиты, независимые документы и общий Retry-After; исключить двойной
   POST при повторном клике и автоматический повтор после ошибки.
4. Проверить drag-and-drop, клавиатуру, отмену диалога выбора, повторный выбор
   того же файла, переходы между лендингом, загрузкой и отчётом.

**Готово, когда:** сгенерированный DOCX проходит реальную проверку, а ошибки не
создают фиктивный успешный отчёт и не запускают скрытых повторов.

### Этап 5. Реализовать новое рабочее пространство отчёта

1. Собрать сводку, фильтры, список, подробности и панель действий по экрану 03.
2. Подключить серверные данные, выбор замечания, все места, копирование,
   раскрытия, отметки и сохранение отметок для конкретного отчёта.
3. Реализовать экраны 06–12 и состояния элементов 15; фильтр и поиск применяются
   ко всему отчёту, а не только видимой части прокручиваемого списка.
4. Добавить доступный блок `warnings` и `limitations` с отдельными заголовками.
   Даже при нуле предупреждений ограничения остаются доступны.
5. Реализовать узкую и мобильную компоновку, сохранить переключатель документов.

**Готово, когда:** каждое замечание и каждое его место доступны; фильтрация и
ручные отметки не меняют серверные счётчики, а детали не остаются от скрытого пункта.

### Этап 6. Завершить автоисправление, скачивание и ошибки

1. Подключить экраны 04, 05, 13 к `/fix` и GET состояния известного документа.
2. После успеха заменить отчёт целиком ответом сервера, переопределить выбор и
   пространство отметок, разрешить скачивание только по `download_url`.
3. После сбоя сохранить доступный предыдущий отчёт и его отметки; проверить,
   не успела ли операция завершиться на сервере после обрыва соединения.
4. Реализовать все ошибки из контракта, используя оформление экрана 14.
   Не ограничиваться шестью иллюстративными сообщениями из макета.

**Готово, когда:** полный цикл «сессия → загрузка → отчёт → исправление → новый
отчёт → скачивание» проходит с настоящим API, включая неуспешное исправление.

### Этап 7. Визуальная и функциональная приёмка

1. Сравнить снимки лендинга и рабочих состояний с эталонными экспортами при
   одинаковых размерах окна. Проверять геометрию, типографику, изображения,
   цвета, переносы, прокрутку и состояния элементов.
2. Проверить 1440 × 900 и 1120 × 900 по макету; дополнительно 768, 390 и 320 px,
   небольшую высоту окна, масштаб 200%, клавиатуру и reduced motion.
3. Проверить реальные Chrome/Chromium, Firefox и Safari, включая мобильный
   Safari либо доступный эквивалент; недоступные окружения явно отметить.
4. Выполнить проверки раздела 6, исправить регрессии и убрать старые стили,
   неиспользуемые обработчики и дубли ассетов.
5. Обновить `docs/FRONTEND.md` и раздел интерфейса `docs/PROJECT.md` по факту
   реализации. `BACKEND.md` менять только в затронутых частях, например описании
   тестов; будущий дизайн не описывать как уже работающий до внедрения.

**Готово, когда:** все критерии раздела 7 выполнены, отличия от макета перечислены,
приложение запускается прежней командой без нового сервера или этапа сборки.

Порядок: 1 → 2 → 3 → 4 → 5 → 6 → 7. Визуальную проверку проводить также после
каждого готового экрана, не откладывая её целиком до последнего этапа.

## 6. Проверки реализации

### Автоматические

```bash
.venv/bin/python -m pytest tests -q
node --test tests/frontend*.test.mjs
```

Сохранить действующие проверки и дополнить их поведением, которое действительно
меняется при редизайне:

- Выбор файла, смена и drop не отправляют POST; явный запуск отправляет один.
- Лимит берётся из сессии; 429/503 блокируют запуск во всех документах вкладки,
  не блокируя чтение и скачивание; окончание паузы не запускает запрос.
- Выбор замечания работает при повторяющихся `rule_id`, смене фильтра и скрытии
  отмеченного; индекс отметки не превращается в позицию отфильтрованной строки.
- Различаются все четыре состояния отсутствия отчёта/замечаний/совпадений.
- Исправленная версия заменяет старый отчёт; ошибка исправления сохраняет
  прежний отчёт и отметки; пустой отчёт после исправления не скрывает скачивание.
- Переключение документа во время операции не подменяет текущий экран ответом
  другого документа и не переносит отметки между документами.
- После обновления страницы и при недоступном localStorage соблюдается контракт.
- Проверить безопасный вывод строк с HTML-подобным содержимым, несколько мест,
  пустой раздел, неизвестное свойство, отказ Clipboard API и длинные значения.

Для UI-тестов с управляемой сетью допустимы фикстуры ответов. В приложении
демонстрационные данные не заменяют запросы. Браузерный сквозной сценарий
обязательно выполнить с реальным API и сгенерированным DOCX.

### Сквозная и визуальная проверка

Локальное приложение запускать с отдельным временным `STORAGE_DIR`; тестовые
DOCX генерировать во временном каталоге. Рабочее `storage/` не использовать
и не очищать. Не запускать второй API с тем же хранилищем.

Проверить: обычный отчёт; отсутствие замечаний; 40+ и большой синтетический
список; длинные фрагменты; несколько мест; только `review`/`recommendation`;
неудачное исправление; восстановление известного UUID; две независимые операции;
неверный формат/размер, 401, 403, 404, 408, 409, 422, 429, 500, 503, 504, 507
и обрыв сети. Редкие отказы воспроизводить тестовыми средствами, не заполняя
настоящий диск и не повреждая рабочие документы.

Визуальные фикстуры отделить от production-кода. Длинный список сначала
реализовать обычным DOM со скроллом и одной панелью деталей; виртуализацию
рассматривать только при измеренной проблеме, а не как обязательный этап MVP.
