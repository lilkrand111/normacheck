# Подготовка Docker-деплоя NormaCheck

Подготовлены изменения бэкенда, фронтенда, контейнеры и локальные проверки
(пункты 2–5 плана). Настройка самого VPS, DNS и публичный запуск выполняются
отдельно. Целевой сервер: Ubuntu 24.04, 1 CPU, 1 ГиБ RAM, 3 ГиБ swap,
25 ГБ SSD. Документы начинают накапливаться с нуля.

## Состав

- `Dockerfile`: Python 3.12, зависимости из `requirements.lock`, UID/GID 10001,
  один Uvicorn и несколько дочерних DOCX-процессов. Target `runtime` — рабочий
  образ, `test` — отдельный образ с Python-тестами и dev-зависимостями.
- `compose.yaml`: приложение и Caddy в отдельной сети. У `app` нет публичных
  портов; только Caddy публикует TCP 80/443. HTTP/3 не включён в публикацию портов.
- `deploy/Caddyfile`: HTTPS для заданного домена, ограничение тела запроса,
  тайм-ауты, проксирование без буферизации целого запроса и без повторов POST.
- `.env.example`: настройки без секрета. Compose передаёт переменные явно;
  Python по-прежнему не загружает `.env` самостоятельно.
- `deploy/check_compose.py`: изолированная локальная сквозная проверка.

Node 22+ нужен только для frontend-тестов, в рабочем образе его нет.
Документы, секреты, `.git`, локальные окружения и кеши не входят в build context.

## Настройки защиты

Загрузка и исправление делят один token bucket на IP: пополнение
`RATE_LIMIT_PER_MINUTE / 60` разрешений в секунду, запас `RATE_LIMIT_BURST`.
По умолчанию это средние 12 запросов в минуту и до 4 подряд, а не строгие
12 запросов в любом скользящем минутном окне. Неверные сессия/CSRF не расходуют
разрешения. Авторизованные попытки расходуют их даже при последующем 422/503.
Повторный POST `/fix` с готовой копией тоже учитывается, но не исправляет файл снова.

Порядок загрузки: сессия/CSRF → частота → слот → multipart → сохранение →
проверка. Ограничитель не читает тело и не создаёт запись документа при отказе.
Глобальные слоты включают загрузку: при двух занятых новая операция сразу
получает 503. Готовые отчёты и скачивание слотов и разрешений не расходуют.

При 429 возвращаются `error.code=rate_limited` и целочисленный `Retry-After`.
При 503 сохраняется `Retry-After: 5`. Интерфейс приостанавливает новые загрузки
и исправления текущей вкладки на этот срок, включая drag-and-drop и переключение
документа. Скачивание, чтение и опрос статуса остаются доступны. По истечении
паузы действия снова доступны, автоматического POST нет. Другие вкладки
проверяются сервером независимо от состояния UI.

Неактивные IP-счётчики очищаются, активные не вытесняются. Таблица ограничена
`RATE_LIMIT_MAX_CLIENTS` (4096). При заполнении неизвестные IP получают 429;
новая cookie не сбрасывает лимит IP. Счётчики не содержат документов и не
сохраняются между перезапусками. Это защита ресурсов приложения, не защита
канала VPS от распределённой сетевой атаки. Пользователи за одним NAT делят лимит.

Срок приёма тела: `UPLOAD_TIMEOUT_SECONDS=120` с начала HTTP-запроса,
пауза между частями — `UPLOAD_IDLE_TIMEOUT_SECONDS=30`. Превышение даёт 408.
После приёма DOCX отдельно действует `PROCESSING_TIMEOUT_SECONDS=60`.
Закрытие файлов незавершённого multipart гарантируется зафиксированной версией
Starlette и проверяется тестами. Принятые исходники и результаты не удаляются.

## Ресурсы и данные

Первоначальный Compose-профиль (уточняется по замерам на VPS):

| Ресурс | Приложение | Caddy |
| --- | --- | --- |
| Физическая память, максимум | 640 МиБ | 96 МиБ |
| RAM + swap, максимум | 2560 МиБ | 192 МиБ |
| CPU, максимум | 0,9 CPU | Планировщик хоста |
| Число процессов/потоков, максимум | 64 | 64 |

ОС и Docker остаётся около 288 МиБ из 1 ГиБ, поэтому фактическую свободную память
нужно проверить. Swap на хосте настраивается отдельно; Compose его не создаёт.
`memswap_limit` — суммарный предел RAM и swap. Два worker с `WORKER_MEMORY_MB=768`
имеют отдельные ограничения виртуального адресного пространства; это не
резервирование 1536 МиБ физической RAM. Профиль не гарантирует обработку любых
DOCX: постоянный swap, тайм-ауты и OOM требуют пересмотра лимитов или VPS.

`app` работает с read-only корнем, без Linux capabilities и с запретом повышения
привилегий. `/data` — bind mount существующего каталога `STORAGE_PATH`;
Compose намеренно не создаёт этот каталог автоматически. Он должен принадлежать
UID/GID 10001 и иметь права 0700. На VPS пример подготовки:

```bash
sudo install -d -m 0700 -o 10001 -g 10001 /var/lib/normacheck/storage
```

Для служебного tempfile используется отдельный дисковый volume `app_tmp`,
не RAM-backed tmpfs. В нём нет постоянных документов. Основные данные не
входят в образ или Docker volume и переживают пересоздание контейнера.
Их не удаляют ни при обновлении, ни для освобождения диска.

Caddy хранит сертификаты и состояние в volumes `caddy_data`/`caddy_config`.
Не удаляйте их при обновлении. У обоих сервисов `unless-stopped`, логи ограничены
3 файлами по 10 МиБ на сервис. Healthcheck приложения раз в 30 секунд обращается
к `/health` с разрешённым Host. `unhealthy` само по себе не вызывает перезапуск;
внешнее наблюдение за доступностью относится к следующему этапу эксплуатации.

## IP, Host и HTTPS

Uvicorn доверяет forwarded-заголовкам только от фиксированного IP Caddy
`172.30.76.2` в выделенной сети `172.30.76.0/29`. В образе без Compose доверие
пустое. Сам ограничитель использует `request.client.host`, не читает заголовки.
Caddy игнорирует присланные посетителем `X-Forwarded-*` и устанавливает свои.
Если сеть пересекается с существующей, поменяйте вместе `DOCKER_SUBNET`,
`PROXY_IP` и `APP_IP` (по умолчанию `172.30.76.3`). Оба адреса фиксированы,
чтобы динамическое выделение IP не заняло адрес прокси до его запуска.
Не задавайте доверие `*` и не публикуйте порт приложения.
Внешний CDN перед Caddy требует отдельной настройки доверенных адресов.

`DOMAIN` — одно имя без схемы, порта и пути. В production `SITE_ADDRESS` не
задаётся, Caddy получает домен из `DOMAIN` и использует HTTPS. Для сертификата
нужны DNS на VPS и доступные TCP 80/443. `COOKIE_SECURE=true` требует постоянный
`APP_SECRET` от 32 символов; генерируйте его один раз и сохраняйте при обновлении.
Конфигурацию храните вне Git с правами 0600. Не выводите полную Compose-конфигурацию
или inspect окружения в общедоступные логи: там может быть секрет.

Прокси допускает 22020096 байт (21 МиБ): файл 20 МиБ плюс 1 МиБ на multipart.
При изменении `MAX_UPLOAD_MB` пересчитайте `MAX_REQUEST_BODY_BYTES`:
`MAX_UPLOAD_MB * 1048576 + 1048576`. Лимиты самого DOCX и ZIP проверяет приложение.
Ответы ранних отказов прокси могут быть не JSON; клиент это поддерживает.

Тайм-аут прокси для загрузки — 130 секунд, ожидания заголовков ответа — 200 секунд,
то есть с запасом на загрузку 120 + обработку 60. Uvicorn ждёт остановки текущих
запросов до 210 секунд, Docker — 220. Если меняете сроки приложения, согласуйте
их с `PROXY_UPLOAD_TIMEOUT`, `PROXY_RESPONSE_TIMEOUT`, CMD Dockerfile и
`stop_grace_period`. Параллельные API с одним хранилищем запускать нельзя.

## Локальные проверки (пункт 5)

Из корня репозитория, с Python 3.12 и dev-зависимостями:

```bash
.venv/bin/python -m pytest tests -q
node --test tests/frontend*.test.mjs
docker build --target runtime -t normacheck:check .
docker build --target test -t normacheck:test .
docker run --rm --memory 640m --memory-swap 2560m --cpus 0.9 normacheck:test
.venv/bin/python deploy/check_compose.py --image normacheck:check
```

Docker daemon должен быть запущен. На macOS ARM эта сборка проверяет Linux ARM64;
для AMD64 VPS нужен образ под AMD64 или сборка на соответствующей машине.
Для повторяемого релиза фиксируйте тег/дайджест образа приложения и базовых образов.
Публичные значения `DOMAIN`, `APP_SECRET` и рабочий storage для этой проверки не нужны.

Скрипт сам создаёт приватный временный каталог, секрет, сгенерированный DOCX,
отдельный Compose-проект, сеть, bind mounts и свободные loopback-порты.
Использует сеть `172.30.77.0/29`; не запускайте две копии проверки одновременно.
Проверяет конфигурацию Caddy, healthcheck, UI/API, CSRF, чужую сессию, hash
исходника, исправление/скачивание, две одновременные загрузки, сохранность после
пересоздания app и невозможность обойти 429 через поддельный X-Forwarded-For.
Для функциональной части запас разрешений повышен до 64, после пересоздания
понижен до 1 для проверки 429. Остальные ресурсные пределы соответствуют Compose.

После проверки скрипт останавливает только свой проект. Сгенерированные данные
и диагностика остаются в указанном временном каталоге; рабочий `storage/` не
используется. С `--keep-running` выводятся URL для браузерной проверки и точная
команда остановки. Не публикуйте содержимое `check.env`.

## Следующие этапы

На VPS предстоит подготовить Docker, swap и каталог данных, защитить постоянную
конфигурацию, измерить нагрузку, подключить домен и проверить HTTPS. Пример
проверки подготовленной production-конфигурации (секрет не выводится):

```bash
docker compose --env-file /etc/normacheck/app.env config --quiet
```

Эта подготовка не настраивает DNS, внешний сервер, резервное копирование,
автоматизацию релизов и наблюдение. При будущих обновлениях сначала прекращайте
приём новых операций, дожидайтесь текущих и сохраняйте тот же storage и секрет.
